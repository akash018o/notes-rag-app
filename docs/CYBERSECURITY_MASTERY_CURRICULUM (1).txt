#### Day 4–5: Common Protocols Deep-Dive
**What you'll learn**: HTTP/HTTPS, SSH, FTP, DNS — how they work, how they're attacked

**Learn** (3 hours):
- SANS Cyber Aces **"Web Fundamentals"**: https://www.cyberaces.org/
- TryHackMe: **"What is Networking?"** room

**Protocol breakdown**:

**HTTP/HTTPS** (Web traffic):
- HTTP = unencrypted, HTTPS = encrypted
- Structure: `GET /path HTTP/1.1`, headers, body
- Attacker can: sniff traffic (HTTP), inject code, steal cookies
- Defense: Always use HTTPS, validate input

**SSH** (Secure Shell):
- Used to remotely login to servers
- Public-key cryptography (we'll learn this later)
- Attacker can: brute-force passwords, steal private keys
- Defense: Key-based auth, strong passphrases, disable root login

**DNS** (Domain Name System):
- Translates names to IPs
- Queries not encrypted (DNSSEC fixes this)
- Attacker can: DNS spoofing, cache poisoning, redirect to fake site
- Defense: DNSSEC, monitor DNS queries

### Week 7–8: Cryptography Basics

**Why this matters**: All modern security relies on cryptography. You need to understand it at a deep level.

#### Day 1–2: What is Cryptography?
**What you'll learn**: Encryption, decryption, symmetric vs. asymmetric, hashing

**Read** (3 hours):
- SANS Cyber Aces **"Cryptography"**: https://www.cyberaces.org/
  - Read all sections carefully
- Khan Academy **"Cryptography"** (free): https://www.khanacademy.org/computing/computer-science/cryptography
  - Watch first 3 videos (15 min each)

**Core concepts**:

| Concept | Explanation | Example |
|---------|-------------|---------|
| **Plaintext** | Unencrypted message | "Hello World" |
| **Ciphertext** | Encrypted message | "K1m0 V0r1k" (Caesar cipher) |
| **Key** | Secret used to encrypt/decrypt | "shift by 3" |
| **Encryption** | Convert plaintext → ciphertext | Plaintext + Key → Ciphertext |
| **Decryption** | Convert ciphertext → plaintext | Ciphertext + Key → Plaintext |

**Symmetric Encryption** (one key for both encrypt & decrypt):
- Same key encrypts and decrypts
- Fast, but key distribution problem
- Examples: AES-256, DES (outdated)
- Problem: How do you securely share the key?

**Asymmetric Encryption** (two keys: public + private):
- Public key: Anyone can see it, used to encrypt
- Private key: Only you have it, used to decrypt
- Slower, but solves key distribution problem
- Examples: RSA, ECC
- Used for: HTTPS, SSH, email signing

**Hashing** (one-way encryption):
- Can't decrypt (by design)
- Used for: passwords, file integrity, digital signatures
- Examples: MD5 (broken), SHA-256, bcrypt
- Properties: Same input → always same output, tiny change → completely different output

**Exercise** (2 hours):
1. Understand Caesar Cipher (shift each letter by N positions):
   - "HELLO" shifted by 3 → "KHOOR"
2. Write a simple Caesar cipher (pen & paper or code):

   ```python
       result = ""

               result += shifted
           else:

       return result

   ```

#### Day 3–5: Modern Cryptography
**What you'll learn**: How HTTPS/SSL/TLS works, RSA basics, why cryptography fails

**Read** (3 hours):
- SANS Cyber Aces **"SSL/TLS"**: https://www.cyberaces.org/
- Khan Academy **"RSA Cryptography"** (5-min video): https://www.khanacademy.org/computing/computer-science/cryptography/rsa-encrypt-and-decrypt

**How HTTPS Works** (critical for SOC analysts):
1. Browser connects to server (port 443)
2. Server sends certificate with public key
3. Browser generates random session key
4. Browser encrypts session key with server's public key
5. Server decrypts with private key
6. Both now use session key for encrypted communication

**Why this matters**:
- Attackers can't read HTTPS traffic (encrypted)
- But attackers CAN see: destination IP, domain, traffic volume, timing
- Attackers CAN intercept if certificate is fake (man-in-the-middle attack)

**RSA Basics** (you don't need to implement it):
- Uses two large prime numbers
- Very hard to factor large numbers (security basis)
- Public key: product of two primes
- Private key: the two primes themselves
- Anyone with public key can encrypt, only private key can decrypt

#### Day 6–7: Hashing & Password Security
**What you'll learn**: Why passwords are hashed, common attacks, why some hashes are weak

**Read** (2 hours):
- SANS Cyber Aces **"Password Security"**: https://www.cyberaces.org/
- Krebs on Security **"Password Tips"**: https://krebsonsecurity.com/password-tips/

**How passwords SHOULD work**:
1. User enters password
2. System hashes it (one-way function): `hash("mypassword123") = a1b2c3d4...`
3. On login, hash entered password and compare to stored hash
4. If hashes match, password was correct
5. Even if database is stolen, passwords aren't immediately readable

**Common password hashing algorithms**:
| Algorithm | Strength | Speed | Status |
|-----------|----------|-------|--------|
| MD5 | Very weak | Very fast | BROKEN - don't use |
| SHA-1 | Weak | Fast | BROKEN - don't use |
| SHA-256 | Medium | Medium | OK for non-passwords |
| bcrypt | Strong | Slow | BEST for passwords |
| Argon2 | Very strong | Slower | BEST for passwords |

**Why bcrypt is strong**:
- **Salting**: Adds random data to password before hashing (prevents rainbow tables)
- **Key stretching**: Hashes the hash multiple times (slows down brute-force)
- **Work factor**: Configurable difficulty (can increase over time)

**Common password attacks**:
- **Dictionary attack**: Try common passwords (password123, qwerty, etc.)
- **Brute force**: Try all combinations (a, aa, aaa, ... zzz...)
- **Rainbow tables**: Pre-computed hashes (useless against salted hashes)
- **Credential stuffing**: Use passwords from other breaches

**SQL Injection** (most common web attack):
```sql
-- Normal SQL query:
SELECT * FROM users WHERE username='admin' AND password='password123'

-- Attacker enters: admin' OR '1'='1
SELECT * FROM users WHERE username='admin' OR '1'='1' AND password='anything'

-- This always returns TRUE, so attacker logs in without knowing password!
```

**Cross-Site Scripting (XSS)**:
```html
<!-- Normal web comment: "Great product!" -->

<!-- Attacker enters: <script>alert('hacked')</script> -->
<!-- This JavaScript runs when others view the page -->
<!-- Real attackers steal cookies/session tokens instead of alert -->
```

**Authentication Bypass**:
```
Normal login: username + password check
Broken auth: No password check, just username in URL
Example: /profile?user=admin (attacker changes "admin" to anyone)
```

# PART 3: DEFENSIVE SKILLS & SOC WORK (Weeks 17–24, September–October)
## Goal: Learn to detect and respond to attacks, build SOC analyst skills

### Week 17–18: Log Analysis & SIEM Basics

**Why**: SOC analysts spend 80% of time looking at logs. You need to be excellent at this.

**Concepts**:
- **Log**: Record of system/application activity
- **Log aggregation**: Collecting logs from all sources into one place
- **SIEM** (Security Information & Event Management): Tool for log analysis, alerting, reporting
- **Log levels**: DEBUG, INFO, WARNING, ERROR, CRITICAL

**Common log sources**:
- System logs: Authentication (login), service changes, errors
- Web server logs: HTTP requests, errors, access patterns
- Firewall logs: Traffic allowed/blocked, port scans
- Application logs: Errors, warnings, user actions
- Database logs: Queries, connections, modifications

**Learn Splunk** (free tier, most popular SIEM):
- Download: https://www.splunk.com/en_us/download.html (free, 500MB/day limit)
- Or use online lab: TryHackMe Splunk rooms (free)

**Exercise** (4 hours):
1. Install Splunk on Ubuntu VM:
   ```bash
   # Download Splunk .tgz file
   # Extract and run
   ./splunk/bin/splunk start
   ```
2. Access Splunk: http://localhost:8000
3. Upload sample logs (download from: https://github.com/splunk/attack_data)
4. Create searches:
   ```
   # Find failed login attempts
   source=auth.log "failed password"
   
   # Find high-volume traffic
   source=access.log | stats count by src_ip
   
   # Find errors
   level=ERROR
   ```
5. Create a dashboard showing:
   - Failed logins over time
   - Top error types
   - Traffic by source IP
6. Screenshot the dashboard

**Check-in**: Send dashboard screenshot.

### Week 19–20: Intrusion Detection & Threat Hunting

**Why**: You need to know what "normal" looks like to spot anomalies.

**Concepts**:
- **Baseline**: Normal behavior (baseline traffic is 100 Mbps, logins are 8am-6pm)
- **Anomaly**: Deviation from baseline (traffic spike to 1Gbps, login at 3am)
- **Indicator of Compromise (IOC)**: Evidence of attack (malware hash, suspicious IP, unusual process)
- **Threat hunting**: Proactive search for threats, not reactive

**Learn threat hunting** (3 hours):
- TryHackMe: **"Threat Hunting"** room (free)
- SANS **"Threat Hunting Fundamentals"** (free whitepaper)

**Sigma Rules** (open-source detection rules):
```yaml
title: Suspicious PowerShell Download
detection:
  condition: keywords all
  keywords:
    - 'powershell'
    - 'DownloadString'
    - 'http'
```

**Exercise** (4 hours):
1. TryHackMe: "Threat Hunting" room
2. Create 3 threat hunts:
   - Hunt 1: Find potential SQL injection attempts in web logs
   - Hunt 2: Find brute-force login attempts in auth logs
   - Hunt 3: Find unusual data exfiltration (large file transfers to outside IPs)
3. For each hunt:
   - Write the search query
   - Screenshot results
   - Explain: What would indicate a real attack?
   - Write a Sigma rule to detect it

**Check-in**: Send hunts + Sigma rules.

### Week 21–22: Incident Response

**Why**: When attacks happen, you need to respond quickly and correctly.

**Incident Response Framework** (NIST):
1. **Preparation**: Tools, processes, training ready
2. **Detection & Analysis**: Identify attack, gather evidence
3. **Containment**: Stop the attack from spreading
4. **Eradication**: Remove attacker access
5. **Recovery**: Restore systems to normal
6. **Post-Incident**: Learn, improve

**Learn incident response** (3 hours):
- TryHackMe: **"Incident Handling"** room (free)
- SANS **"Incident Handler's Handbook"** (free PDF)

**Incident response playbooks** (step-by-step procedures):
```
MALWARE DETECTION PLAYBOOK
1. Isolate affected machine (disconnect network)
2. Collect evidence (memory dump, disk image)
3. Scan with antivirus + manual analysis
4. Determine spread (check other machines)
5. Remove malware
6. Restore from clean backup
7. Update AV signatures
8. Brief management
```

**Exercise** (4 hours):
1. TryHackMe: "Incident Handling" room
2. Create incident response playbooks for:
   - Playbook 1: Ransomware attack
   - Playbook 2: Data breach (attacker accessed database)
   - Playbook 3: Malware on employee machine
3. For each playbook:
   - Step-by-step actions
   - Who to involve
   - What evidence to collect
   - Timeline estimation
   - Communication strategy

**Check-in**: Send playbooks.
